# comxkit Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans for native execution, or superpowers:subagent-driven-development if the user selects delegation. Implement task-by-task using checkbox steps. This document is a plan, not an instruction to start implementation. Work in the current checkout; do not commit or push.

**Goal:** Ship an installable `comxkit` CLI that visibly presents supported stack choices, initializes a runnable Gin/Ent/PostgreSQL project, and safely adds domain and CRUD resource scaffolds.

**Architecture:** Cobra and Huh resolve user input into plain planning inputs. A private generator renders embedded templates into a validated file plan; one filesystem writer owns conflict checks, staging and rollback. Generated applications own concrete business code and import go-common infrastructure, with generated registration files handling incremental assembly.

**Tech Stack:** Current module Go version (currently 1.27.3), released Cobra, Huh v2, existing Ent/Gin/PostgreSQL integrations, existing YAML v3 implementation, standard `embed`, `text/template`, `go/format`, SHA-256 and filesystem APIs. Choose and pin released CLI/Atlas versions during implementation after checking their actual module paths and compatibility.

**Spec:** [2026-11-08-comxkit-design.md](../specs/2026-11-08-comxkit-design.md)

## Global Constraints

- Preserve all pre-existing dirty paths in `/Users/nhan.huynh1/coding/self/go-common`. No reset, stash, commit, push, or new worktree unless requested.
- Only implement `gin`, `ent`, `postgres`; show all three categories even when each has a single choice. Use one registry for forms, flags, help/completion and compatibility.
- Use injected Cobra commands, `RunE` and command contexts. No global command variables, `init()` registration, Viper, Fang or custom command framework.
- Huh is private to the interactive CLI. Both flag and form paths invoke the same generator; no generator imports of Cobra/Huh and no runtime imports of CLI dependencies in generated applications.
- Default schemas use existing `UUIDMixin` (UUIDv7) and `TimeMixin`. Optional existing `SoftDeleteMixin` and `ModifierMixin` include their required wiring. No new `IDMixin` or invented business fields.
- Models/requests/metadata are plain data. Services own validation and business decisions; repositories own persistence. Do not redesign `pkg/database.Repository` during this feature.
- Default operations: Find, Get, Create, Update, Delete. Optional Upsert/GetBulk/CreateBulk/UpdateBulk/UpsertBulk/DeleteBulk. Use the `Bulk` suffix; there is no FindBulk.
- Page size default 10, maximum 100. Bulk default maximum 100; reject empty requests and duplicate target IDs. Bulk writes use one transaction; GetBulk preserves requested order and fails if any ID is missing.
- Upsert requires an explicit UUID ID conflict target in this release, and never restores a soft-deleted record. Do not invent domain uniqueness or a fields DSL.
- Generated applications use existing context-aware logger, HTTP wrappers, lifecycle, health, transaction and error helpers. Do not generate request IDs or a new response envelope.
- `init` performs filesystem generation only: no Git initialization, dependency/tool installation, Docker startup, DB connections, migration generation or external scripts. `--dry-run` makes no filesystem changes.
- New-project destination must be absent or empty. Never overwrite user-owned source; regenerate owned files only against their recorded hashes. Reject paths escaping the project, symlink writes and concurrent mutations.
- Selected stack, schema/generator version, registrations/options and ownership hashes live in `.comxkit.yaml`; credentials and business field definitions do not.
- Released kit versions pin a matching released go-common version. Development builds require `--common-version` if build metadata cannot supply one. No unresolved placeholder or external filesystem `replace` in generated go.mod.
- `make run-local` applies checked-in SQL only. No schema auto-create on API startup and no implicit migration diff, seed or reset. Preserve `.env` and database volumes.
- Follow the user AGENTS.md: meaningful top-down tests. No constant spelling, constructor field-copy, plain model serialization, whitespace-only golden tests or production branches added solely for coverage.

## Review Focus

1. Cancel or fail while adding a resource: user source, metadata and registration must remain consistent; Task 2 tests staging failure/cancellation and interruption detection.
2. Add another resource after the first Ent client exists: no rewritten custom code, duplicate initialization/close, invalid empty-schema generation or import cycles; Tasks 3/4/7 test init-only, domain-only and multi-resource projects.
3. Run unattended with incomplete/invalid input or redirect stdout: never hang or start a form; flags and interactive selection resolve identically; Tasks 1/8 cover non-TTY, stream routing and selection equivalence.
4. Retry bulk/upsert around soft deletion or a concurrent missing row: never revive deleted data or partially commit writes; Tasks 5/6/7 exercise transactional behavior against PostgreSQL through HTTP.
5. Use a development kit, an edited generated registration, a stale file plan, or a malformed migration chain: fail explicitly without emitting broken dependencies, clobbering files, or generating SQL implicitly; Tasks 1/2/4/9 pin those outcomes.

## Shared Interfaces

Define these once in Tasks 1/2; later tasks consume the same signatures:

```go
type Options struct {
    In io.Reader
    Out, Err io.Writer
    WorkDir, Version, CommonVersion string
    Interactive bool
}
func NewCommand(options Options) *cobra.Command

type InitInput struct { Directory, Module, HTTP, ORM, Database, CommonVersion string }
type DomainInput struct { Name string }
type ResourceInput struct {
    Name, Domain, Route, UpsertOn string
    Operations []string
    SoftDelete, Modifier bool
}
type PlannedFile struct { Path string; Content []byte; ExpectedHash string; Owned bool }
type Plan struct { Root, Kind string; Files []PlannedFile; NoOp bool }
type Result struct { Root string; Created, Updated []string; NoOp bool }

type generator interface {
    Init(context.Context, InitInput) (Plan, error)
    Domain(context.Context, string, DomainInput) (Plan, error)
    Resource(context.Context, string, ResourceInput) (Plan, error)
    Apply(context.Context, Plan) (Result, error)
}
type prompter interface {
    Project(context.Context, InitInput, Registry) (InitInput, error)
    Resource(context.Context, ResourceInput, Registry) (ResourceInput, error)
    Confirm(context.Context, Plan) (bool, error)
}
```

`Registry` contains descriptor data, not model methods. Command input resolution and generator implementation use package functions. `ExpectedHash` is empty for create-only files and is the exact SHA-256 precondition for replacements. Plans include the original metadata hash as the replacement precondition; metadata does not hash itself. A private `newCommand` constructor injects registry/prompter/generator for behavior tests; production `NewCommand` composes their real implementations.
